# ISA 项目讨论与开发决策

日期：2026-11-18  
项目：ISA（游戏玩法决策助手）  
讨论范围：知识库与问答边界、Modular RAG 约束、长期产品方向

## 1. 项目目标

### 1.1 初期目标

初期只聚焦《明日方舟》集成战略「黑流树海」玩法，先搭建可持续更新的知识库，使 AI 能够基于有来源的知识理解：

- 游戏事实与机制；
- 玩法流派、运营思路和打法；
- 资料中的适用条件、例外和版本范围。

初期通过开发脚本和测试直接调用问答用例，不开发交互式 CLI 或 Web，不要求图片识别。提交问题后，系统检索当前版本知识，进行简单分析并给出行动建议，同时说明依据、适用前提、风险和未知项。

### 1.2 最终目标

最终形态是采用 PySide6 + Qt Quick/QML 的桌面应用或后台游玩助手，重视视觉效果，能够：

- 自动识别游戏画面；
- 更新局内资源和状态；
- 在需要时提供决策建议；
- 说明建议的机制依据、攻略依据和不确定性；
- 整合攻略，帮助玩家理解玩法、形成运营思路，并促进玩法传播。

桌面壳、持续读屏、OCR 拓扑识别和局内自动更新属于后续能力。初期通过应用层用例和稳定契约为这些能力保留接入边界，不提前实现。

## 2. 最终决策

### 2.1 版本策略

- 新资料和新版本追加保存，不覆盖旧资料。
- 版本记录不可变；资料审核状态与版本范围分别记录。
- 新版本先进入 draft，完成整理和审核后由用户手动设置为 active。
- active 选择按 `source_id + Scope` 持久化为当前 `document_id`；所选文档须已发布且审核通过。每个 source/scope 只有一个当前选择，替换选择不覆盖旧文档。
- 默认检索 active 版本；系统不按字符串或抓取时间自动决定当前版本。
- `as_of` 只筛选内容适用时间，不用于推导 active 选择。每次运行固定请求时的 active selection、文档清单、`as_of`、允许的 `evidence_kinds` 和检索配置；active 切换不改变历史运行。

### 2.2 资料策略

初始资料由用户人工整理，输入可以来自网页截图、其他图片和 Markdown。图片作为原始证据保存；人工清理内容、优化排版并整理成 Markdown 后再入库。初期不要求自动 OCR。

知识采用“结构化声明 + 原文证据”双轨：

- 事实与机制使用结构化声明表达名称、条件、效果、例外、版本和状态；
- 玩法流派与攻略保留章节化文本，记录作者观点、适用条件、版本和来源定位；
- 两类知识都关联原始来源和定位信息；
- 只有已审核、版本匹配的内容才进入默认检索和生成上下文。

### 2.3 Modular RAG 三层

Modular RAG 必须保持三层边界：

```text
编排层（调度）
  → 模块层（预检索 / 检索 / 后处理 / 生成）
    → 算子层（最小可替换单元）
```

编排层负责选择流程、传递上下文、处理成功/失败/未知状态和保存链路信息。模块层表达可理解的能力阶段。算子层提供可替换实现，例如查询预检索、关键词召回、向量召回、证据过滤、回答生成和引用校验。

初期使用 Python 显式流程与类型化状态，三层必须清晰存在。调度使用可解释的规则和配置，不让模型自由拼接任意模块。Haystack Pipeline 是后期流水线扩展备选，当前不引入框架。执行进度、业务结果和记录结果分别建模，状态转换、有限重试、取消与统一收尾按[技术选型决策](technology-selection.md)约束。

### 2.4 核心算子契约

核心算子必须遵循：

```text
输入契约 → 输出契约 → 配置快照
```

每个核心算子至少声明：

- 输入类型、字段和前置条件；
- 输出类型；
- 成功、失败、未知和空结果状态；
- 算子标识、实现版本和配置快照；
- 证据引用或定位信息（如果该算子产生或筛选证据）；
- 副作用边界。

日志、指标记录和简单过滤等辅助算子可以采用轻量实现，但不得破坏核心算子契约和链路错误传递。

### 2.5 Agent 定位

用于优化 Modular RAG 的 Agent 属于算子层，而不是独立回答者。它可以：

- 拆解复杂问题；
- 选择或组合底层 RAG 接口；
- 针对常规流程无法解决的问题提出下一步检索计划。

它不能绕过证据独立回答、发布知识、修改 active 版本、认定游戏规则或替代确定性校验。初期不实现 Agent，先用固定调度流程建立基线。

### 2.6 初期固定流程

```text
脚本/测试提交问题
  → QueryPrecheckOperator
  → HybridRetrieveOperator
  → EvidenceFilterOperator
  → AnswerGenerateOperator
  → CitationValidateOperator
  → RecordOperator
  → 输出结果
```

所有核心算子通过统一契约接入。默认检索采用 Dense + BM25 召回、RRF 融合和 Cross-Encoder 精排；已审核术语精确命中用于 BM25 查询扩展，`pg_trgm` fuzzy 是可独立记录并参与 RRF 的候选通道。`RerankMode=disabled` 仅可显式配置用于实验或降级，须记录模式、原因和事件。双路及融合归 HybridRetrieveOperator，资格复核后精排与证据选择归 EvidenceFilterOperator 的具名子步骤，保留六个顶层算子。检索通道和精排模式以实际运行快照为准。

### 2.7 错误与未知状态

核心算子失败必须显式失败，不能静默降级。错误必须结构化，并随链路上下文传递到后续阶段，至少包含错误类型、来源算子、消息、可读详情、是否可重试和链路位置。

允许配置明确的降级路径，例如向量召回失败后改用关键词召回，但降级必须产生结构化事件并进入运行记录。证据为空、版本不匹配、引用校验失败和资料不足都必须保留为可识别状态。

### 2.8 RecordOperator

`RecordOperator` 是独立算子，记录完整链路。至少包括：

- `chain_id`、`run_id`、请求 ID、父链路 ID（如有）；
- 开始/结束时间、耗时、环境和应用版本；
- 用户原问题、规范化问题和上下文摘要；
- `scope`、`as_of`、允许的 `evidence_kinds`、active selection ID、文档/声明清单及版本选择依据；
- 调度器选择的流程、模块和算子顺序；
- 每个核心算子的标识、实现版本、配置快照、输入/输出摘要和状态；
- 召回候选、最终证据、来源定位和证据快照引用；
- 实际启用的检索通道、BM25 词典/索引版本、RRF 与 rerank 配置和降级事件；
- 生成请求、模型标识、回答和引用校验结果；
- 结构化错误、未知项、降级事件和重试信息；
- 每个阶段和整条链路的耗时、计数和指标；
- 可回放所需的输入、规则、检索配置、模型和内容哈希。

原始资料、大向量和大文件通过内容哈希及文件/快照引用关联，不直接复制进单次运行记录。

## 3. 初期功能完整设计

### 3.1 用户流程

```text
输入问题
  → 读取 active 版本
  → 预检索并识别问题类型/术语
  → Dense + BM25 召回，可按配置加入 fuzzy 通道，以 RRF 融合
  → 过滤版本、审核状态和证据资格
  → 默认 Cross-Encoder 精排并组织证据上下文
  → 生成解释与建议
  → 校验引用
  → 保存完整链路
  → 返回脚本/测试可检查的结果
```

回答至少包含：

- 结论或建议；
- 相关机制解释；
- 玩法流派或攻略依据；
- 适用前提；
- 风险和可能的反例；
- 未知项或需要补充的信息；
- 可定位的来源引用。

### 3.2 知识库能力

初期需要支持：

- 来源和原始附件登记；
- Markdown 文档导入；
- 人工清理后的标题、章节和定位；
- 版本、玩法范围和审核状态；
- 结构化事实/机制声明；
- 流派、攻略和观点文本；
- 术语、别名和常见表达；
- 可替换的递归/结构/语义/领域切片算子，初期结构优先、超长递归，无父子切片；
- 中文 BM25、Dense/fuzzy 召回、RRF 融合与可配置 Cross-Encoder 精排的可替换实现；
- 证据定位、引用快照和检索运行记录；
- active 版本切换和历史版本查询。

### 3.3 初期明确不实现

- 桌面壳和系统级后台驻留；
- 持续读屏和自动资源更新；
- 自动地图拓扑识别；
- 自动发布 OCR 或模型抽取结果；
- 自由规划的多 Agent 系统；
- 独立向量数据库、独立搜索集群或微服务拆分；
- 完整路线搜索和复杂局内状态机（先为后续能力保留接口）。

## 4. 当前项目边界

当前建设范围是《黑流树海》知识库和有引用的问答闭环，包括人工整理资料、知识版本与审核、切片和混合检索、回答与引用校验、完整运行记录，以及通过固定样本进行验证。开发入口为 Python 脚本和测试，直接调用应用用例。

当前不开发交互式 CLI、Web 或桌面 UI；不实现自动 OCR、局面识别、持续读屏、自动资源更新、完整路线搜索或 Agent。PySide6 + Qt Quick/QML 是最终桌面方向，待相应能力进入开发范围后另行设计。后续能力不得作为当前问答链路的前置依赖。

每项实际开发工作使用统一 Markdown 模板，记录当前需求、用户场景、相关技术、方案与架构、数据模型与接口、实现步骤、验收标准、实验结果、设计取舍和未解决问题。文档描述代码与已确认决策的当前状态，不记录临时阶段安排或修改历史。

## 5. 统一任务文档模板

```markdown
# 任务名称

## 1. 应用需求
## 2. 用户场景与输入输出
## 3. 相关技术
## 4. 方案与架构
## 5. 数据模型与接口
## 6. 实现步骤
## 7. 验收标准
## 8. 实验记录与结果
## 9. 设计决策与取舍
## 10. 未解决问题与后续决策
```

任务文档必须记录失败实验和未采用方案，避免重复试错。完成标准是代码、契约、验收结果和文档相互一致。
