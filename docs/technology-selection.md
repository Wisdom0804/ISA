## 1. 应用需求

### 1.1 依据与适用范围

产品与知识规则依据[项目讨论与开发决策](project-discussion.md)，执行约束依据[开发规范](../AGENTS.md)。[总体架构设计](isa-architecture-design.md)描述当前知识库与问答的模块边界、数据模型和后续能力边界；本文记录技术选择及其验证状态。工具角色依据见[官方资料核验](official-sources.md)与[框架资料核验](research-rag-tools.md)；第三方事实参考不替代本文的项目选型结论。

当前优先完成「黑流树海」知识库与有引用问答用例，通过 Python 脚本和测试验证，不开发交互式 CLI 或 Web。最终桌面采用 PySide6 + Qt Quick/QML，重视视觉效果，但当前不实现；后续项目结构需要考虑 QML、Python 界面适配与核心用例的隔离。

知识采用“结构化声明 + 原文证据”，资料追加保存，版本先为 draft，人工审核后由用户手动设置 active。active 选择按 source 与 Scope 记录所选 document 版本；审核 approved 不会自动激活。默认回答仅使用 active、已审核、版本匹配且来源合格的证据；历史运行固定当时的选择、内容和配置。模型、检索分数和框架都不能替代审核或认定游戏规则。

### 1.2 环境与取舍原则

| 条件 | 当前依据与处理 |
|---|---|
| 本机环境 | Windows；24 核 CPU、32 GB 内存，RTX 5070 笔记本独显 8 GB，另有用户提供的集显 16 GB 信息；不把独显与共享内存相加当作 CUDA 显存 |
| 基础设施 | 已有 PostgreSQL 与 Docker，复用而不假定二者部署位置；本任务不连接或操作数据库 |
| 模型 | 初期本地 BGE-M3 dense；生成通过 API 能力契约接入，供应商后续确定 |
| 性能 | 不设当前耗时/吞吐门槛，但保留资源、耗时、超时和取消观测；不编造显存可用性或质量结果 |
| 工程原则 | 正确性、证据、显式失败和可回放优先；以稳定契约实现可替换，不为“工业化”引入无需求的微服务、队列或通用图引擎 |

### 3.4 检索召回、融合与精排

**已确定：默认使用 Dense 与 BM25 召回、RRF 融合和 Cross-Encoder 精排。** 已审核术语精确命中只扩展 BM25 查询，不单独产生候选通道；`pg_trgm` fuzzy 候选是独立通道并参与 RRF。仅 Dense、仅 BM25、显式启用/停用 fuzzy 或 `RerankMode=disabled` 均须由实验或已配置降级明确选择，封存实际配置并记录事件，不允许静默切换。

| 功能模块 | 选型决策 | 选型理由 | 未选方案及理由 | 注意事项 |
|---|---|---|---|---|
| Dense 召回 | 本地 BGE-M3 dense + pgvector/HNSW，cosine | 语义匹配补充不同问法和攻略描述 | 不仅靠关键词；不引入 FAISS/Qdrant/Milvus 第二规范存储 | 相近机制不等于条件相同；版本与审核资格硬过滤 |
| 词法召回 | BM25；首个工程实现采用 jieba + 已审核游戏词典、bm25s | 专名、缩写、数字和词项相关性与 Dense 互补；无需独立服务 | n-gram 等值匹配不代替 BM25；ts_rank 不称为 BM25；rank_bm25 可作小样本对照，不维护双套生产实现 | 分词器、词典、统计清单、BM25 变体和参数锁定；不按空格拆中文，不照搬会删除否定/条件的停用词表 |
| 查询精确扩展 | 已审核术语/别名用于 BM25 查询扩展，不单独形成候选通道 | 精确术语改善 query 表达，同时保留 BM25 统一排名 | 不把精确命中结果另行混成 RRF 通道 | 记录原 query、扩展项、词典 revision 和扩展理由 |
| 模糊候选 | pg_trgm 作为独立 `fuzzy` 候选通道参与 RRF | 将近似术语候选与 BM25/Dense 来源区分并可单独评测 | 模糊命中不改写审核词典，也不替代 BM25 | 记录相似度和通道 rank；候选仍须通过相同版本、审核和来源资格 |
| 向量查询 | HNSW 主查询，精确 cosine 作为评测/显式补查 | 已选近似索引，保留可检查的精确对照 | 不以无性能约束为由撤回 HNSW，不同时建设 IVFFlat 路线 | 近似结果可能受过滤影响；记录构建和查询参数、实际扫描/补查路径 |
| 融合 | RRF，以各路排名形成候选池 | 不直接混合不同尺度原始分数，可解释、易回放 | 不直接相加 Dense/BM25 分数，不初期训练排序模型 | 保存各路分数/排名、权重、常数、融合分和并列规则；RRF 不补回两路均漏掉的证据 |
| 精排 | Cross-Encoder；首个本地基线采用 BAAI/bge-reranker-v2-m3 | 对问题与候选联合评分，进一步识别相关性和条件 | 不用 Embedding 相似度冒充精排，不用 LLM 自评取代确定精排阶段 | 模型与 BGE-M3 是两个模型；锁 revision、输入构造和长度策略，分数不代表事实概率；选中精排后失败不能自动绕过 |
| 证据选择 | 资格复核、精排、去冗余、完整证据预算 | 控制进入生成的证据质量与内容 | 不无条件把融合 top-k 全塞模型，不以高分抵消未审核/版本错误 | 相同文本不同来源保留定位；去重不可丢失来源；不得静默截去关键条件 |

jieba/bm25s 和具体 reranker 是本方案的首个工程基线，发行版本、模型 revision 与兼容性仍是实施锁定项。替换库须保留相同业务契约并通过评测，不构成自动切换授权。

#### 工业化执行要求

1. **冻结请求上下文。** 接收问题后固定 active 选择、scope、必填 `as_of`、非空允许的 `evidence_kinds`、实际文档/声明/片段清单、词典、切片、向量空间、模型和生效配置；`as_of` 筛选适用时间，不回溯推导 active 选择。使用可校验的内容哈希关联，运行中不重选“最新”。
2. **检查索引就绪。** Dense 与 BM25 的清单与查询一致；词法索引同时校验 token、统计量和 chunk ID 映射。不得用全库 top-k 后过滤冒充同一资格集合内的召回。
3. **显式召回通道。** Dense 与 BM25 默认独立返回排名、原始分数、状态及耗时；启用 fuzzy 时也独立返回明细。各通道可顺序执行，不要求线程并发；集中汇合，禁止并发修改共享候选表。
4. **正确处理 HNSW 过滤。** SQL 包含资格条件，但不能据此声称近似扫描物理上先过滤。按选定 pgvector 版本配置 iterative scan、参数或同一合法集合精确补查；不足保留计数和事件，数据库异常不借补查静默转成功。
5. **稳定合并与 RRF。** 以候选实例 ID 合并，公式为 sum(w_channel / (rrf_k + rank_channel))，rank 从 1 起，未命中贡献 0，按固定 ID 打破并列。零词项匹配返回空词法候选，不用任意零分文档凑数。
6. **受控精排。** 在资格复核后的融合池内，发送明确的 query/passage 文本；记录全部精排输入/哈希、模型和输出。超长片段按固定窗口/聚合规则处理并保留定位，或显式要求重新切片，不由 SDK 无声截断。
7. **封存生成证据。** 精排相关性默认决定排序，RRF 用于并列和追溯，不未经定义叠加两种分数。选中证据包含条件、例外和来源；上下文预算只移除完整证据并记录实际发送内容。
8. **可靠性与副作用。** 模型、数据库、文件调用设超时与有限重试；重试需可重试分类和副作用约束。不存在“任意失败换个 provider 就继续”；降级有专门配置与事件，不足/失败保持可辨识。
9. **质量闸门。** 同一语料和问题上运行 Dense、BM25、RRF、RRF+Cross-Encoder 四组消融，检查候选 Recall@k、排序 nDCG/MRR、证据覆盖及引用支持度。覆盖专名、别名、数值、否定、条件和版本；失败样本不从分母静默移除。
10. **配置与发布。** 候选配额、RRF 常数/权重、HNSW 参数、BM25 k1/b、重排长度及证据预算都封存实际值；未经评测不称“最优”。新模型/索引先构建、校验和评测，再人工确认使用，不修改历史运行引用。

PostgreSQL 保存规范语料、版本和索引清单；bm25s 文件是可重建派生物，不是第二业务数据库。BM25 的 IDF/长度统计范围和版本必须明确；索引清单不匹配时显式失败或进入独立重建任务，不能静默读取旧索引。原件、词法索引和向量重建不能覆盖仍被历史运行引用的版本。

参考：[检索后重排](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)、[bm25s](https://github.com/xhluca/bm25s)、[jieba](https://github.com/fxsjy/jieba)、[pgvector 过滤](https://github.com/pgvector/pgvector#filtering)、[BGE reranker](https://huggingface.co/BAAI/bge-reranker-v2-m3)。

### 3.5 Embedding 与模型适配

| 功能模块 | 选型决策 | 选型理由 | 未选方案及理由 | 注意事项 |
|---|---|---|---|---|
| 初期 Embedding | 本地 BGE-M3 dense，1024 维、L2 归一化、cosine | 固定模型与预处理，适合中文/多语言资料，沿用已确认方向 | API 不作当前实现；sparse/multi-vector 非本轮所需，不扩展模型输出面 | 维度不等于整个空间定义；revision、池化、tokenizer/预处理、query/document 策略均固定 |
| 推理接入 | Sentence Transformers/PyTorch 为初始适配，统一 EmbeddingProvider | dense 与 Cross-Encoder 可在同一模型生态适配 | 不同时维护 FlagEmbedding 等多套等价实现；特定 sparse 能力出现时再评估 | 保存真实模型输入哈希和输出关联；验证维度、有限、非零及实际范数 |
| 后续替换 | API/其他本地模型通过新空间接入 | 接口稳定，模型可替换 | 不只改模型名后混用旧向量，不以 API 接入改变审核规则 | 模型/预处理变化需重建；缺少不可变 revision 的供应商要记录限制和实际响应 |
| 执行设备 | CPU/CUDA 显式配置 | 不把设备绑定到业务契约 | 不静默 GPU 转 CPU，不把 8 GB 当双模型同时驻留保证 | 验证实际驱动与 PyTorch 构建；可顺序加载，不承诺和游戏同时运行时的显存 |

参考：[BGE-M3](https://huggingface.co/BAAI/bge-m3)、[Sentence Transformers](https://www.sbert.net/)。

### 3.6 Modular RAG 调度与框架

| 功能模块 | 选型决策 | 选型理由 | 未选方案及理由 | 注意事项 |
|---|---|---|---|---|
| 当前调度 | Python 显式流程 + 类型化状态 | 当前流程明确，直接控制前置条件、错误与记录，无需框架状态侵入 | LangGraph 当前不引入，不预设迁移路线；Dify 等平台增加适配和运行成本 | 状态和转换规则见第 5 节；不写巨型 if/else，不自制通用工作流引擎 |
| 后期扩展备选 | Haystack Pipeline | RAG 组件和连接语义贴近检索、融合与精排，适合组件增加后的复用 | 不将 Haystack Agent 与 Pipeline 混同；不因组件存在就接管领域或数据所有权 | 引入前做局部适配验证；仅一个调度权威，ISA 契约、资格与记录仍保留 |
| 模型/Agent 框架 | 当前不引入 Pydantic AI、pydantic-graph、DeepSeek Harness | 当前无需 Agent 循环或另一图/运行时；保持必要依赖 | Pydantic AI 不替代整条 RAG，pydantic-graph 是额外图框架；DeepSeek Harness 属另一 Agent 运行环境 | 已有 Pydantic 不等于已有 AI 框架；候选事实保留在核验记录，不是当前技术决策 |

## 4. 方案与架构

### 4.1 已确定的层次与职责

采用模块化单体。RAG 固定“编排层 → 模块层（预检索/检索/后处理/生成）→ 算子层”。界面和基础设施不拥有审核、active 选择或游戏规则。

固定顶层流程为：

```text
QueryPrecheckOperator → HybridRetrieveOperator → EvidenceFilterOperator
→ AnswerGenerateOperator → CitationValidateOperator → RecordOperator
```

| 顶层算子 | 当前职责 |
|---|---|
| QueryPrecheckOperator | 检查问题与范围，规范化/审核术语处理，固定后续检索所需上下文 |
| HybridRetrieveOperator | Dense 与 BM25 默认召回，按配置加入 fuzzy 通道，汇合并以 RRF 排序，输出带通道明细的候选 |
| EvidenceFilterOperator | 资格复核、按 RerankMode 执行 Cross-Encoder 精排或显式跳过、去冗余与上下文预算，输出实际生成证据 |
| AnswerGenerateOperator | 仅用选中证据及必要输入组织请求，返回回答草稿与生成记录 |
| CitationValidateOperator | 校验回答结构、引用 ID、实际发送证据与定位，输出校验结果 |
| RecordOperator | 统一封存成功/失败/未知/空证据/取消及链路事件 |

Dense/BM25/RRF 与精排是具名子步骤，有独立输入输出、版本、配置、状态和子链路位置；不增加第七个顶层算子。切片属于导入，不混入问答链。前序失败或无法继续时停止依赖结果的业务步骤，标注下游未执行原因并进入记录，不为了走完顺序继续无证据生成。

### 4.2 扩展边界

后期仅指定 Haystack Pipeline 为流水线扩展备选。引入时将现有算子包装为组件，统一一套调度权威；领域契约、状态语义、版本和 RecordOperator 不交给框架隐式管理。框架检查点和日志可关联为附件，不能替代规范记录，也不能据此承诺副作用 exactly-once。

项目目录、单向依赖与最终桌面 MVVM 的接入约束见[项目结构与骨架搭建指南](project-structure.md)。骨架按能力任务逐步建立；当前不创建 QML 资源或桌面实现。

## 5. 数据模型与接口

### 5.1 类型化状态模型

以下是当前确定的语义模型，字段精确定义在核心契约任务中实现。执行进度、业务结果和记录结果分开，避免用一个 status 或多个布尔值表达互相矛盾的事实。

| 模型 | 核心字段与语义 | 写入/所有权 |
|---|---|---|
| RunContext | chain_id、run_id、request_id、parent_chain_id、时间、环境/应用版本、scope、as_of、evidence_kinds、active selection ID/依据、文档/声明/索引清单、配置与哈希 | 编排入口创建，冻结后只读；缺少合格 active 选择时显式保留错误，不扩大语料 |
| ChainState | lifecycle、当前步骤、business_outcome、typed_outputs、step_records、errors、unknowns、events、record_status | 仅调度器通过受控转换更新，不向算子暴露可任意修改的全局对象 |
| OperatorResult[T] | outcome、类型化可选输出、结构化错误/未知、证据引用、事件、实现版本与实际配置快照 | 算子返回，调度器验证并接纳；失败不能同时伪装有有效业务输出 |
| StepRecord | operator_id、子步骤位置、attempt、开始/结束与耗时、执行状态、输入/输出摘要和哈希 | 每次尝试追加，不覆盖前次失败；跳过步骤记录原因 |
| ChainError | type、source_operator、message、details、retryable、chain_position，可附 attempt/因果关联 | 技术错误与业务状态分开保留；未知异常映射后不丢原始诊断 |
| RecordResult | record_status、持久化引用、校验信息或记录错误 | RecordOperator 返回；调度器接纳，不递归触发自身记录 |

状态值域：

| 维度 | 值域 | 含义 |
|---|---|---|
| lifecycle | initialized / running / finalizing / completed | 只表达调度进度；completed 不等于业务成功 |
| step_status | pending / running / succeeded / failed / cancelled / skipped | 一次尝试是否执行及技术状态；成功但空结果由 outcome 表达 |
| outcome | success / empty_evidence / insufficient_evidence / version_mismatch / citation_invalid / unknown / failed / cancelled | 算子或整条业务结果；业务不确定不能压成普通成功或技术异常 |
| business_outcome | 未终结时 null；终结时取上述 outcome | 只在业务结论明确时定值，记录失败不覆盖原业务结果 |
| record_status | not_started / writing / stored / failed | 业务留痕结果，独立于生成与引用状态 |

约束：success 必须满足对应输出和前置条件；证据空不能继续正常生成；citation_invalid 不得对外标成已验证回答；failed 必须带结构化错误；未知项不是通用异常替身。明确配置的降级可产生有边界的结果，但必须有事件，不抹除原失败。执行状态、知识审核状态、版本生命周期绝不共用一组枚举。

### 5.2 状态转换与终结

| 条件 | 调度动作 | 结果约束 |
|---|---|---|
| 请求接收且输入可建模 | initialized → running，创建只读上下文，进入首步 | 无效输入也尽可能记录已知请求，不编造 active 或证据 |
| 算子 success，满足下一步前置 | 接纳输出，步骤 succeeded，进入固定下一步 | 不通过算子自行指定任意 next_step |
| empty/insufficient/version/unknown 等阻止继续 | 固定 business_outcome，下游业务步骤 skipped，转 finalizing | 保存原因；没有正常答案与“成功”伪装 |
| 可重试技术失败 | 按错误分类和配置尝试同一步，追加 attempt/event | 有次数和截止上限，不跨终结边界自动重试，不重复不可安全重试副作用 |
| 不可恢复失败或重试耗尽 | business_outcome=failed，保留原因，下游 skipped，转 finalizing | 不捕获后返回空列表冒充成功 |
| 用户取消 | 标记取消请求，终止后续调度，按能力取消当前调用，转 finalizing | 不声称无法终止的远端调用已停止；取消不跳过记录 |
| 引用通过 | business_outcome=success，转 finalizing | 仍须记录成功才能对外确认整次成功 |
| finalizing | record_status=writing，调用一次记录逻辑，可有配置内的有限尝试 | 记录逻辑不自调度自己，不允许无限收尾循环 |
| 记录成功 | record_status=stored，lifecycle=completed | 保留原 business_outcome；只有业务 success 且 stored 才报告整体成功 |
| 记录失败 | record_status=failed，lifecycle=completed，附加 RECORD_FAILED | 不覆盖原始业务错误，不报告已保存；返回可追踪诊断 |

记录写入的是业务终态和截至收尾的完整链路。RecordOperator 自身的版本、配置、耗时、尝试和记录结果应由存储实现纳入提交元数据/回执；不要求记录算子递归记录自己。不得用两张互相覆盖的状态快照制造“全部记录已完整保存”的假象。记录失败时其自身错误无法保证进入同一故障存储，须通过返回结果和诊断保留，不能宣称可靠持久化。

初期没有进程崩溃后断点恢复承诺。非正常进程终止可能留下未完成运行，后续查询应标示未完成而非成功；是否加入启动时恢复/核对由运行记录任务单独设计。

### 5.3 Python 调度避免失控的规则

1. **单一调度权威。** 顶层只认固定执行计划、结果类型和有限转换；算子不决定路由、不修改别的步骤，不用共享 dict/布尔旗标叠加隐式状态。
2. **状态单一写入口。** 调度器集中校验前置条件并接纳 OperatorResult，采用不可变结果/受控更新；纯契约不包含 ORM 会话、Qt 对象或框架 State。
3. **分支就近封装。** Dense/BM25 的执行和汇合在混合检索算子内，重排在后处理内；顶层不理解 SQL、token 或模型调用细节，子步骤仍可追踪。
4. **错误与策略分开。** 算子报告事实与错误，调度器按显式政策决定有限重试、降级或终止；禁止 except 后空结果、无限循环及 provider 私自切换。
5. **收尾集中。** 成功、失败、空证据、未知、取消都进入同一 finalizing 规则，记录失败保留原因；记录不能递归进入记录。
6. **副作用可界定。** 算子声明读写边界；重试前检查幂等/去重方案，索引和知识发布不夹在检索或生成中执行。
7. **控制复杂度。** 只实现当前实际分支，不造图 DSL、自动插件发现或检查点系统；新增分支必须补转换表、状态不变量和测试，再评估维护成本。
8. **扩展不双重调度。** 若引入 Haystack，先用固定案例验证资格、失败、重试和记录，再逐步替换调度适配；不同时运行两套互相覆盖的状态机。

### 5.4 模型与输出契约

| 接口 | 必需能力 | 注意事项 |
|---|---|---|
| EmbeddingProvider | ID/文本/哈希与 space 输入，按 ID 对齐向量、维度、模型、版本及状态 | 超长显式处理；有限、非零、范数检查；不同空间重建，不混写 |
| RerankProvider | 原问题或固定构造 query、候选 ID/文本/哈希，返回对应分数、模型/实现版本及状态 | 逐项对齐，不把漏返回当低分；固定长度/窗口/聚合；精排与召回模型分开；由 RerankMode 明确启用或禁用 |
| GenerationProvider | 指令、问题、必要上下文与带 ID 证据，生成文本及可获得元数据 | 设输入输出上限、超时/有限重试；原生 JSON、streaming、工具调用非必须 |
| AnswerResult | 建议、机制、前提、风险、未知、引用及校验结果 | 与供应商消息分开；未经引用校验不得当已验证答案 |
| CitationResult | 结构、证据 ID、实际发送文本与来源定位的检查结果 | 不把确定性检查声称为语义蕴含证明 |

认证、限流、超时、服务异常映射为结构化错误，不可区分时明确未知技术错误。配置模型标识和可获得 revision；服务不提供的 token、费用或 request_id 允许为空，不编造。密钥不进入记录；本地取消不等于远端服务已停止计费。

### 5.5 运行记录的完整性

RecordOperator 至少封存：链路/运行/请求/父关联、时间和耗时、环境和应用版本、原问题及规范化问题、上下文摘要、`scope`、`as_of`、允许的 `evidence_kinds`、active selection ID/依据及文档/声明清单、流程与模块/算子顺序、每个核心算子的实现版本/配置/输入输出摘要/状态、启用通道及 BM25 词典/索引版本、RRF/rerank 模式与参数、召回候选和最终证据、来源定位/快照、生成请求/模型/回答/引用验证、错误/未知/降级/重试/阶段指标，以及回放所需输入、规则、检索配置、模型与内容哈希。

Dense/BM25/RRF/精排各子步骤与 attempt 可在同一链路定位。大文件、原件和大向量以哈希/引用关联，不复制进单次运行。回放读封存结果，重算另建 run；不以当前 active、模型或文件路径覆盖历史语义。
